======================================================================
CONTEXTE
======================================================================

Cette version commence le chantier de persistance demandé par le projet.

Objectifs :
- rendre l'écriture de data.json plus sûre ;
- éviter qu'une modification partielle efface des données ;
- ne modifier l'état mémoire qu'après confirmation de l'écriture disque ;
- ajouter un test automatisé minimal de persistance ;
- conserver un historique permanent des modifications.

Cette version ne met pas encore en place la sauvegarde automatique à chaque
saisie utilisateur. Elle stabilise d'abord la couche de persistance utilisée
par les routes de sauvegarde existantes. L'autosave temps réel sera traité
dans une phase dédiée.

======================================================================

alors que la persistance a échoué.

par la requête, notamment pour :
- stats ;

des champs qu'elle ne connaît pas encore.

Date : 10 août 2026

PROBLÈME RAPPORTÉ
-----------------

Lorsqu'un HP était modifié depuis fiche_perso.html, la valeur affichée dans
interface_jeu.html ne changeait pas.

CAUSE IDENTIFIÉE
----------------

interface_jeu.html initialisait ses champs à partir des query parameters de
l'URL et ne les relisait pas ensuite.

En parallèle, server.js émettait déjà l'événement Socket.IO :

    playerUpdate

mais interface_jeu.html ne l'écoutait pas.

Le problème était donc une absence de consommation du système temps réel,
et non une absence de sauvegarde serveur.

CORRECTION
----------

Fichier modifié :

    website/interface_jeu.html

Modifications :

1. Ajout du client Socket.IO.

2. Après chargement initial, l'interface récupère l'état officiel du joueur
   depuis :

    GET /api/joueurs

3. Ajout de :

    refreshPlayerFromServer()

4. Ajout de :

    applyAuthoritativePlayerState(joueur)

5. Ajout d'un listener :

    socket.on('playerUpdate', ...)

Lorsqu'un événement concerne le joueur actuellement affiché, l'interface
recharge immédiatement son état depuis le serveur.

6. Les valeurs synchronisées sont également reportées dans l'URL afin que
   "Voir Fiche de Perso" ne reparte pas d'une ancienne valeur.

COMPORTEMENT CIBLE
------------------

Fiche perso
    ↓
Modification HP
    ↓
POST /api/joueur
    ↓
Persistance data.json
    ↓
server.js
    ↓
playerUpdate
    ↓
Interface de jeu
    ↓
GET /api/joueurs
    ↓
HP actualisé immédiatement

IMPORTANT
---------

Cette version utilise encore le nom du joueur pour retrouver l'entité dans
GET /api/joueurs.

Le passage à un identifiant stable reste prévu dans une phase ultérieure.

VERSION v1.3 — IDENTIFIANTS STABLES DES PERSONNAGES
Date : 10 août 2026
======================================================================

OBJECTIF
--------

Supprimer progressivement la dépendance au nom du personnage comme
identifiant technique.

Le nom reste une donnée affichée et modifiable.

L'identité technique du personnage devient un ID stable.

PROBLÈME AVANT v1.3
-------------------

Plusieurs flux utilisaient :

    joueur.nom

comme identité technique :

- mise à jour ;
- suppression ;
- identification dans l'interface ;
- synchronisation temps réel ;
- ouverture des fiches.

Cela devient fragile si deux personnages portent le même nom ou si un nom
est modifié.

MIGRATION DES DONNÉES
---------------------

Chaque personnage existant dans data.json reçoit un ID au format :

    char_<UUID>

Les IDs sont générés une seule fois et deviennent persistants.

Les données de jeu existantes sont conservées.

joueur.js effectue également une vérification au démarrage afin de pouvoir
ajouter un ID à un ancien personnage qui en serait dépourvu.

MODIFICATIONS TECHNIQUES
------------------------

1. joueur.js

Ajout :
- génération d'ID ;
- getJoueurById();
- recherche prioritaire par ID ;
- sauvegarde par ID ;
- suppression par ID ;
- conservation de l'ID lors d'une modification ;
- génération automatique d'un ID lors de la création.

La recherche par nom reste disponible comme mécanisme de compatibilité.

2. server.js

Ajout :

    GET /api/joueurs/:id

Les endpoints de mise à jour acceptent maintenant :

    id

et conservent le nom uniquement comme fallback de compatibilité.

Les événements playerUpdate contiennent maintenant :

    playerId

en plus du nom.

La création d'un joueur retourne également son playerId.

La suppression utilise désormais l'ID.

Un endpoint legacy par nom est conservé sous :

    DELETE /api/joueurs/delete-by-name/:nom

3. popupjoueur.js

Ajout de :

    PlayerId

dans les URLs des fiches.

4. popupmj.js

Ajout de :

    PlayerId

dans les URLs des fiches ouvertes par le MJ.

5. interface_jeu.html

La synchronisation utilise désormais :

    /api/joueurs/:id

lorsqu'un PlayerId est disponible.

Le nom reste uniquement un fallback pour les anciennes URLs.

Le listener playerUpdate compare prioritairement playerId.

6. fiche_perso.html

La fiche récupère PlayerId depuis son URL.

Lors d'une sauvegarde, elle envoie l'ID au serveur.

Le nom n'est envoyé comme identifiant que si aucune ID n'est disponible,
afin de conserver la compatibilité avec les anciennes URLs.

L'ID retourné par le serveur est conservé dans l'URL.

7. selecte_player.html

Les cartes utilisent joueur.id comme data-id.

La suppression utilise l'ID stable.

8. mj.html

Les cartes utilisent joueur.id comme data-id.

9. tests/persistence.test.js

Le test vérifie maintenant :
- présence d'un ID ;
- recherche par ID ;
- modification par ID ;
- conservation de l'ID ;
- persistance de la modification ;
- conservation des champs non modifiés.

COMPATIBILITÉ
-------------

Les anciennes URLs sans PlayerId restent supportées grâce au fallback par nom.

La migration vers les IDs est donc progressive et ne nécessite pas de
recréer les personnages existants.

LIMITES
-------

Cette version ne met pas encore en place :
- un Game ID global ;
- des IDs pour les mobs ;
- des IDs pour les statuts ;
- une refonte complète des URLs ;
- une autorisation basée sur les IDs.

Ces éléments restent à traiter dans les phases correspondantes.

VERSION v1.4.1 — SÉPARATION FICHE DE PERSO / ÉTAT DE SESSION
Date : 10 août 2026
======================================================================

CLARIFICATION FONCTIONNELLE VALIDÉE
------------------------------------

Le comportement attendu est asymétrique :

    Fiche de Perso -> Interface de Jeu
        AUTOMATIQUE

    Interface de Jeu -> Fiche de Perso
        MANUEL

La Fiche de Perso représente les données persistantes du personnage.

L'Interface de Jeu représente l'état du personnage pendant la partie active.

AVANT v1.4.1
------------

Les deux interfaces écrivaient dans data.json via :

    POST /api/joueur

Cela signifiait qu'une modification dans l'Interface de Jeu pouvait modifier
directement les données persistantes de la Fiche de Perso.

Ce comportement ne correspondait pas au besoin réel.

ARCHITECTURE v1.4.1
--------------------

Deux états sont maintenant séparés :

    data.json
        = données persistantes de la Fiche de Perso

    session.json
        = état de la partie active

La session est volontairement unique pour le moment.

FLUX 1 — FICHE DE PERSO -> INTERFACE DE JEU
--------------------------------------------

    Fiche de Perso
          |
          | POST /api/joueur
          v
    data.json
          |
          v
    synchronisation session
          |
          v
    session.json
          |
          v
    playerUpdate
          |
          v
    Interface de Jeu

Ce flux est AUTOMATIQUE.

Une modification de la Fiche de Perso met donc à jour l'état de session
correspondant et l'Interface de Jeu est actualisée automatiquement.

FLUX 2 — INTERFACE DE JEU -> SESSION
-------------------------------------

    Interface de Jeu
          |
          | POST /api/session/player
          v
    session.json

Cette sauvegarde ne touche JAMAIS data.json.

La Fiche de Perso n'écoute volontairement PAS l'événement
sessionPlayerUpdate.

Une modification de l'Interface de Jeu reste donc uniquement dans l'état
de la session jusqu'à ce qu'une future action manuelle de synchronisation
vers la Fiche de Perso soit explicitement développée.

NOUVEAU FICHIER
---------------

    session.js

Responsabilités :
- charger session.json ;
- persister la session de manière atomique ;
- initialiser l'état de session d'un personnage ;
- synchroniser la session depuis une Fiche de Perso ;
- sauvegarder les modifications provenant de l'Interface de Jeu.

NOUVEAU FICHIER DE DONNÉES
--------------------------

    session.json

Il contient uniquement l'état de la partie active.

Le fichier est initialisé à partir des personnages existants.

NOUVELLES API
-------------

    GET /api/session/player/:id

Retourne l'état du personnage dans la partie active.

    POST /api/session/player

Sauvegarde uniquement l'état de session du personnage.

IMPORTANT
---------

POST /api/session/player ne modifie pas data.json.

ÉVÉNEMENTS SOCKET.IO
--------------------

    playerUpdate

Signifie :
    la Fiche de Perso a changé et la session doit être propagée vers
    l'Interface de Jeu.

    sessionPlayerUpdate

Signifie :
    l'état de la partie a changé.

L'Interface de Jeu peut utiliser cet événement pour synchroniser les autres
clients de jeu.

La Fiche de Perso ne l'utilise pas comme mécanisme de mise à jour
automatique.

V1.4 CORRIGÉE
-------------

La logique de "fiche autoritaire" de la v1.4 est conservée pour la Fiche de
Perso elle-même : lorsqu'elle est ouverte avec un PlayerId, elle charge les
données persistantes depuis data.json.

En revanche, l'Interface de Jeu ne charge plus directement data.json pour
son état courant. Elle charge session.json via :

    GET /api/session/player/:id

VERSION v1.4.4 — CORRECTION DU BOUTON D'IMPORT : SCOPE PLAYERID
Date : 10 août 2026
======================================================================

PROBLÈME
--------

Le bouton "Mettre à jour depuis la partie" était visible mais son clic
n'affichait aucune confirmation.

CAUSE
-----

La variable playerId était déclarée à l'intérieur du callback :

    window.addEventListener('DOMContentLoaded', async () => {
      const playerId = ...
    });

Le gestionnaire du bouton était placé dans un autre bloc <script>.
Il ne pouvait donc pas accéder à cette variable.

Le gestionnaire pouvait également ne pas accéder à
loadAuthoritativePlayerState() pour la même raison de scope.

CORRECTION
----------

Le PlayerId courant est maintenant exposé explicitement :

    window.arcanePlayerId

Le chargeur autoritaire de la Fiche est également exposé :

    window.arcaneLoadAuthoritativePlayerState

Le bouton utilise ces références globales de manière explicite.

COMPORTEMENT
------------

Au clic :

    1. récupération du PlayerId ;
    2. affichage de la confirmation ;
    3. POST /api/session/player/:id/apply-to-character ;
    4. rechargement de data.json dans la fiche ;
    5. message de réussite.

Si aucun PlayerId n'est présent, une erreur claire est affichée.

VERSION v1.5 — GESTION DE SESSION : TEMPS RÉEL + EXPORT / IMPORT
Date : 10 août 2026
======================================================================

OBJECTIF
--------

Consolider la notion de partie active et répondre à deux exigences du
projet :

1. chaque modification de l'état de jeu doit être propagée en direct aux
   Interfaces de Jeu concernées ;
2. la partie active doit pouvoir être exportée puis importée sur un autre
   serveur.

1 — SYNCHRONISATION TEMPS RÉEL DE LA SESSION
--------------------------------------------

L'événement Socket.IO :

    sessionPlayerUpdate

est maintenant écouté par Interface de Jeu.

Lorsqu'un joueur modifie son état de session :

    Interface de Jeu A
          |
          | POST /api/session/player
          v
      session.json
          |
          | sessionPlayerUpdate
          v
    Interfaces de Jeu du même joueur

La Fiche de Perso n'écoute pas cet événement.

Le comportement asymétrique v1.4.4 est donc conservé.

2 — EXPORT DE LA SESSION
------------------------

Nouvelle API :

    GET /api/session/export

Le serveur génère un fichier JSON contenant :

- format ArcaneSyncSession
- formatVersion
- date d'export

MODELE DE DONNEES
-----------------

    id, nom, description
    grid       { cols, rows, cellSize, showGrid }
    background { color }
    tokens{}   entites mobiles, referencant char_* ou mob_*
    elements{} decor, obstacles, murs, portes, objets, pieges

Aucune entite n'est dupliquee : un NPC de carte EST un mob de session,

SEPARATION DES DONNEES
----------------------

data.json          fiches de personnage
session.json       partie active (+ activeMapId)

Portee circulaire (distance euclidienne) + ligne de vue par trace de

et la cible ne bloquent pas : on voit le mur qui nous fait face, jamais
ce qui se trouve derriere.

    none    aucune restriction
    vision  champ de vision du personnage du joueur
    manual  zones peintes par le MJ

Evenements

VERSION V1.13.1 - GENERATION DE CARTES PAR TYPE DE LIEU
======================================================================

OBJECTIF
--------

Permettre au MJ de choisir un type de lieu (foret, caverne, batiment,
ruines, ville, plaine) et d'obtenir immediatement une carte jouable,
qui reste ensuite entierement modifiable a la main.

PRINCIPE DIRECTEUR
------------------

Un generateur ne produit AUCUN format special : uniquement des
`elements` standards de map.js. Une carte generee est donc, du point de
vue du reste du systeme, identique a une carte dessinee a la main. Tous
les outils existants (poser, effacer, inspecter, redimensionner,
brouillard, vision) continuent de fonctionner sans adaptation.

FICHIERS CREES
--------------

mapgen.js
    Module PUR (aucune E/S, aucune dependance a la session).
    6 generateurs, materiaux, compactage, garantie de connexite.

tests/mapgen.test.js
    Catalogue, jouabilite des 6 types, determinisme, bornes,
    compactage, regeneration, cablage serveur et interface.

FICHIERS MODIFIES
-----------------

map.js
    + remplacerDecor()   remplace le decor, conserve les tokens
    + trouverCaseLibre() placement hors obstacle
    + casesOccupees()
    ~ synchroniserTokens() ne place plus un personnage dans un mur

server.js
    + GET  /api/map/generators
    + POST /api/maps/generate
    + POST /api/maps/:mapId/regenerate
    + require('./mapgen')

website/map.html
    + panneau "Generer un lieu" (type, taille, densite, graine)
    + bouton d'ouverture / fermeture des portes dans l'inspecteur

package.json
    + tests/mapgen.test.js dans npm test, script test:mapgen

TYPES DE LIEUX
--------------

foret     bruit + lissage cellulaire, clairiere, sentier traversant
caverne   automate cellulaire, cavite principale conservee
batiment  decoupage BSP, salles, couloirs, portes, mobilier
ruines    batiment effondre, murs perces, gravats, vegetation
ville     trame de rues, maisons avec portes, place de marche
plaine    espace ouvert, riviere et pont, bosquets epars

DETERMINISME
------------

La generation utilise un PRNG a graine (mulberry32). Une meme graine et
des memes parametres redonnent toujours exactement la meme carte. Cela
permet de retrouver une carte, de comparer des variantes et de tester.

Si aucune graine n'est fournie, une graine stable est derivee du type et
des dimensions : le resultat reste reproductible.

JOUABILITE GARANTIE
-------------------

Apres generation, garantirConnexite() ne conserve qu'une seule zone
praticable : les poches isolees sont comblees. Les points d'apparition
retournes sont des cases contigues de cette zone, pour que le groupe
demarre ensemble.

Les portes generees sont OUVERTES : la carte est jouable immediatement.
Le MJ peut les fermer d'un clic depuis l'inspecteur, ce qui bloque le
passage ET la ligne de vue ; le champ de vision des joueurs est
recalcule aussitot.

COMPACTAGE
----------

Les cases identiques adjacentes sont fusionnees en rectangles (fusion
horizontale puis verticale). Une caverne passe ainsi de plusieurs
centaines d'elements d'une case a une soixantaine de rectangles :
maps.json reste leger et le decor reste manipulable a la main.

REGENERATION
------------

POST /api/maps/:mapId/regenerate remplace le decor d'une carte existante.

    Tokens                conserves
    Tokens dans un mur    repositionnes sur un point d'apparition
    Memoire d'exploration effacee (elle decrivait un decor disparu)
    Dimensions            conservees par defaut

DROITS
------

Les trois routes de generation passent par refuserSiPasMj(). L'interface
joueur n'expose aucun outil de generation et ne connait pas ces routes.

----------

DECOUPAGE PAR LE BROUILLARD
---------------------------

Un trace qui traverse une zone inconnue est DECOUPE cote serveur : seuls
les fragments situes dans une zone connue du personnage sont serialises.
Le joueur ne peut donc pas deduire la partie cachee depuis la charge
utile reseau.

    zone connue = cases visibles maintenant + cases explorees par le groupe

Deux exceptions volontaires :
    - l'auteur voit toujours ses propres annotations en entier ;
    - le MJ voit tout.

APERCU EN DIRECT
----------------

Pendant le trace, chaque segment part en mapDrawStream : aucune ecriture
disque, simple apercu. Le serveur ne relaie un segment a un joueur que
si TOUS ses points sont dans une zone qu'il connait, et jamais si le
trace appartient au calque MJ.

Au relachement du pointeur, le trace complet est enregistre en une seule
requete POST, puis diffuse par emitMapState comme le reste de l'etat.

DROITS
------

MJ       tracer, ecrire, effacer tout, choisir le calque, autoriser les
         joueurs
Joueur   uniquement si le MJ l'autorise ; son trace est toujours partage
         avec la table ; il ne peut effacer que les siens

Un joueur qui tenterait d'envoyer author:'mj' ou visibleToPlayers:false
voit ces champs ecrases par le serveur.

1. PERSISTANCE - ECRITURE DIFFEREE ET FUSIONNEE          (storage.js)
----------------------------------------------------------------------

MESURE AVANT : maps.json pesait 1,5 Mo. Chaque mutation le reecrivait
INTEGRALEMENT et de facon SYNCHRONE : 58,8 ms (8,2 ms de stringify +
50,6 ms d'ecriture). Un glisser de token sur dix cases bloquait la
boucle d'evenements 588 ms, pendant lesquelles aucune autre requete
n'etait servie.

FICHIER CREE : storage.js
    creerDepot(chemin, {delaiMs}) -> ecrire / ecrireDifferee / flush /
                                     annuler / enAttente
    flushAll() et annulerTout() au niveau module.

Trois proprietes importantes :

  a) FUSION. ecrireDifferee REMPLACE le contenu en attente au lieu de
     l'empiler : dix mutations rapprochees produisent une ecriture.

  b) SERIALISATION PARESSEUSE. ecrireDifferee accepte une FONCTION,
     evaluee seulement au vidage. Sans cela on aurait serialise le
     megaoctet dix fois pour ne l'ecrire qu'une : la moitie du cout
     serait restee sur le chemin critique. Le gain est passe de x5 a x9
     grace a ce seul point.

  c) COHERENCE. Le differe ne rend PAS les mutations asynchrones. La
     mutation memoire reste strictement synchrone ; seul le vidage
     disque est repousse. Les handlers Express ne contiennent aucun
     await : deux requetes ne peuvent donc pas s'entrelacer.

     NOTE : le rapport d'audit classait « lost update » en CRITIQUE.
     C'etait INEXACT et cela a ete corrige avant implementation : le bug
     n'est pas exploitable tant que les handlers restent synchrones.
     C'est precisement la contrainte que respecte ce design.

    + methode surEcriture() sur le depot

server.js
    + socket.on('mapTogglePorte', ({ elementId }) => ...)

    Le role et le personnage sont lus dans le HANDSHAKE, jamais dans le
    message. Un client ne peut donc pas s'annoncer autrement qu'il ne
    s'est connecte. Aucune route REST n'est ouverte aux joueurs.

    Succes -> rafraichirExploration() PUIS emitMapState(). L'ordre
    compte : ouvrir une porte degage une ligne de vue, et sans ce
    recalcul prealable la piece revelee n'entrerait dans la memoire du
    groupe qu'au mouvement suivant.

L'AUTORISATION, ENTIEREMENT SERVEUR

map.js
    + basculerPorte(mapId, elementId, { role, playerId })

      1. l'element existe et son kind est 'porte' ;
      2. pour un joueur : son jeton est SUR la carte ;
      3. adjacence — Chebyshev <= 1 entre le rectangle de la porte et
         celui du jeton (taille du jeton comprise). Pas de controle de
         ligne de vue en plus : etre a portee de bras suffit, et une
         porte adjacente est de toute facon visible ;
      4. la porte n'est pas VERROUILLEE ;
      5. bascule blocksMovement ET blocksVision, et le nom.

      Le MJ ouvre n'importe quelle porte, de n'importe ou, verrouillee
      ou non.

L'ORDRE DES CONTROLES N'EST PAS ARBITRAIRE. Le verrou est verifie EN
DERNIER. Son message revele une information de MJ : il ne doit parvenir
qu'a quelqu'un qui a reellement la main sur la poignee, jamais a un
joueur qui sonderait la carte a distance. La premiere version testait le
verrou en premier ; un personnage meme absent de la carte apprenait
qu'une porte etait verrouillee. Corrige.

LE VERROU, SANS LEQUEL LE MJ PERD UN POUVOIR

Ouvrir les portes aux joueurs retire au MJ un veto qu'il avait
implicitement — lui seul les manoeuvrait. On le lui rend explicitement :

map.js     normaliserElement() gagne `verrouillee`, OMIS quand il est
           faux, comme lightRange en V1.13.8. Le decor d'une carte
           generee compte des centaines d'elements qui n'ont rien d'une
           porte.
map.html   case « Verrouillee » dans l'inspecteur, pour les portes.

`verrouillee` N'EST JAMAIS TRANSMIS AU JOUEUR. Savoir a l'avance qu'une
porte resistera est une information de MJ ; le joueur l'apprend en
essayant.

LES GESTES

map_joueur.html  un clic sur une porte ADJACENTE la manoeuvre. Place
                 APRES la prise du jeton : un personnage pose sur la
                 case d'une porte doit rester deplacable. Le controle

V1.13.12b - CORRECTIF : L AURA N ETAIT PAS CENTREE SUR LE JETON
----------------------------------------------------------------------

Remonte par l utilisateur : « l aura de portee n est pas centree sur le
joueur ».

CAUSE. dessinerAura() calculait son centre en multipliant la case par
cellSize, sans passer par px(). Or px() ajoute la GOUTTIERE — la marge
de 22 px ou sont ecrits les reperes de colonnes et de lignes. Le cercle
etait donc decale de 22 px vers le haut ET vers la gauche, soit 31 px en
diagonale : jamais centre sur le jeton, quelle que soit la portee.

Tout le reste du rendu passe par px() ou pointVersPx(). L aura etait la
seule exception, et c est exactement ce qui se voyait.

CORRECTIF
    map-core.js  cx = px(token.x + taille / 2)
                 cy = px(token.y + taille / 2)

    Cette formule est RIGOUREUSEMENT celle de dessinerToken() :
        px(token.x) + (taille * cellSize) / 2
    developpee, elle donne le meme resultat. Le centre de l aura et
    celui du jeton sont donc calcules a l identique, par construction.

    Verifie numeriquement, jeton 1x1 en (7,4), cellSize 40 :
        centre du jeton      (322, 202)
        aura AVANT correctif (300, 180)  ecart 31,1 px
        aura APRES correctif (322, 202)  ecart 0,0 px

AU PASSAGE. L etiquette « N cases » se place au-dessus du cercle. Sur
une grande portee, le haut du cercle sort du canvas et l etiquette avec
lui. Elle est desormais ramenee a l interieur : elle porte le chiffre,
c est elle qu on vient lire.

TEST DE NON-REGRESSION  (tests/map.test.js)
    le centre de l aura doit etre calcule avec px() ;
    AUCUNE coordonnee de case ne doit etre convertie sans px() dans
      dessinerAura — c est la faute exacte, formulee en interdit ;
    les deux formules sont reproduites et COMPAREES au centre calcule
      par dessinerToken(), seule reference qui fasse foi. Un ecart non
      nul echoue le test.
